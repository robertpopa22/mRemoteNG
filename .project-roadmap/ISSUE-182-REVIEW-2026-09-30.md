# #182: new retention evidence and incorrect measurement verdict

Source: [vndnua's September 29 report](https://github.com/robertpopa22/mRemoteNG/issues/182#issuecomment-5898279242), reviewed September 30.
This is a different reporter from Buster-de, whose September 13 measurements confirmed improvement
in their environment. It does not establish when the newly reported behavior began.

## Verified findings

- Reported baseline: 99 MB. First settled close: 274 MB (+175 MB). Fourteenth settled close:
  1,274 MB (+1,175 MB). After the first close, another 1,000 MB remains over 13 further sessions,
  approximately 76.9 MB/session. The series has intermittent decreases, but no final plateau.
- Reporter used several Windows Server 2008-2025 targets and waited 30 seconds after each close.
  The first-session peak was 431 MB, or 332 MB above baseline.
- The script printed `No accumulation` because its 77 MB average was below half of 332 MB
  (166 MB). Replaying the exact series through the old summary reproduced this false reassurance.
- Absence of `host dispose threw` only excludes that reported error message. It does not prove
  all native/managed allocations were released. Private bytes show retained process allocation,
  but do not identify its ownership or prove an unreachable allocation leak.
- The existing three-cycle xrdp acceptance test in `RdpSessionMemoryAcceptanceTests.cs` uses the
  same half-session-cost threshold. Its green result cannot refute this Windows-target report.
  Do not replace that threshold with another arbitrary cutoff and present it as a memory fix.

## Bounded correction and verification

`scripts/measure-rdp-memory.ps1` now reports the cumulative post-first-close growth, the full
per-close series and the uncertainty. It no longer prints either a definitive leak diagnosis or
a leak-free verdict from this ratio. Exit 0 means the measurement completed; fewer than three
marked closes return 2, consistently with the stated minimum.

Summary-only replay, without opening the application: the supplied 14-close series reports
`+1000 MB across 13 further sessions`; flat and decreasing series report their exact net change
without claiming leak freedom; two closes return insufficient data. All four cases passed.
This validates the reporting correction, not memory release in the product. No product code changed.

## Authorized investigation and independent challenge

The maintainer requested one counteropinion, then implementation and regression tests on September 30.
One adaptive review completed (Mistral, high effort). It agreed that the old ratio cannot establish
absence of retention and that resource counts and valid logins matter. Its proposed forced COM
release and five-cycle/10-20 MB thresholds were not accepted: ownership was unproven, the proposal
shortened the reporter's series, and AxHost already owns COM teardown. The .NET 10 AxHost source
and the actual generated MSTSCLib event provider were inspected. A review is input, not proof.

The Windows Server 2025 lab completed fourteen authenticated sessions, with desktop screenshots and
30-second post-close waits. Before the product change, private bytes rose from 64.1 to 77.7 MiB,
handles from 1,303 to 2,351 and GDI objects from 189 to 485. This reproduced a resource-retention
defect, **not** the reporter's approximately 1,000 MB increase. The different scale remains unexplained.
A local heap snapshot was taken during this diagnostic run; no collection was forced in the app.

The heap established a strong path from the main window's shared theme through ThemeBase's
ToolStrip restoration dictionary, disposed panel menus, ConnectionWindow, ConnectionTab and
AxHost.AxContainer to closed InterfaceControl/RdpProtocol11 objects. Source also showed unremoved
ThemeChanged/resize subscriptions and the last-focused panel/tab cache. ThemeBase.ApplyTo(ToolStrip)
keeps a strong reference until global theme cleanup; cleaning the whole shared theme on every
panel close would disturb other panels and was rejected.

The scoped correction applies the same renderer to transient session menus without registering
them in that global dictionary, removes panel subscriptions/history on disposal, and forgets the
disposed current panel/tab. It does not force GC, trim working sets, or change COM release ownership.
The real form-lifecycle ownership test was run against both DLLs: the old DLL fails; the corrected
DLL releases all fourteen disposed panels. An earlier test harness that manually invoked OnLoad
was discarded because it bypassed WinForms lifecycle flags and itself retained forms.

Validation in progress: full unit suite and the four Windows long-run combinations (tab/panel,
KeepTabs off/on), plus application-exit cases. See [the test contract](../docs/RDP-MEMORY-REGRESSION.md).
No complete product-memory fix or reporter confirmation is claimed at this checkpoint.

### Additional roots exposed by the longer check

The first product candidate still grew from 1,276 to 2,369 handles and 189 to 485 GDI objects
across fourteen Windows closes. A second heap snapshot traced the remaining theme root to the
outer panel menu: DockPanelSuite's DockContentHandler automatically registers tab context menus.
The initial ownership test had bypassed PanelAdder. The expanded test creates real panel menus
and a tab: all 56 watched objects remain alive with that candidate, and none with scoped menu
cleanup. The adapter removes only the disposed strip from DockPanelSuite 3.1.1's private
restoration map; an incompatible library upgrade fails the ownership tests. Global theme cleanup
is never used as per-panel cleanup. Panel menu ownership is explicit, and disposal also removes
the registry entry. Repeated removal initially caused a test exception; the idempotent guard
and a repeated-dispose assertion cover that regression.

A further heap snapshot, after the theme root was removed, exposed a COM reference-counted
handle retaining the generated AxHost event multicaster, its disposed host and the whole session.
The host was already passive, its native-instance field null and its connection cookie disconnected,
but the multicaster still had native reference count 1. This is distinct from a theme reference.

The [.NET 10 ConnectionPointCookie implementation](https://github.com/dotnet/winforms/blob/release/10.0/src/System.Windows.Forms/System/Windows/Forms/ActiveX/AxHost.ConnectionPointCookie.cs)
obtains an IUnknown pointer for the sink without balancing that temporary reference after Advise.
[ComHelpers](https://github.com/dotnet/winforms/blob/release/10.0/src/System.Private.Windows.Core/src/Windows/Win32/System/Com/ComHelpers.cs)
returns the reference acquired by GetIUnknownForObject on this interop path. The lab and local
test host both use Windows Forms 10.0.11. An isolated real-ActiveX ownership test reproduced
retention for all six protocol selections without connecting to a server: three of three hosts
stayed rooted in each case. With the explicit connection-point subscription, all six cases pass.

Implementation scope: preserve each protocol's existing generated AxHost version and event
multicaster; replace only the cookie with a COM-marshaled Advise/Unadvise pair; release only the
connection-point wrapper acquired by that subscription; keep AxHost responsible for its RDP
object; verify both raw hosts and initialized protocol handlers, then rerun the Windows matrix.
No FinalReleaseComObject, working-set trim, forced application GC, or security-setting change is used.

The initialized-protocol extension initially failed for selections 8 through 11, although all
raw hosts passed. Source inspection showed RdpProtocol8's main-window and static display-event
subscriptions were released only by Close, not by Dispose. Direct parent/control disposal
therefore retained the initialized protocol. Cleanup is now shared by both lifecycle paths,
including stopping and disposing the resize timer. The test deliberately retains this direct
disposal path instead of masking it by calling Close first.

### Connected-session teardown

Removing those roots alone did not pass Windows acceptance. A further fourteen-login run
(`9B4E17F63135C8F6B491D900268BFB418F48004C28FF7CB43BD810ADD51054BD`) rose from 1,276 to
2,323 handles and 189 to 485 GDI objects. Its receipt is `requires-investigation`. A heap
snapshot found no roots for the four remaining protocol objects or seven remaining AxHost
objects; this narrows the remaining problem but does not establish native release.

Instrumentation distinguished reading Connected from calling Disconnect: the control reported
Connected=1, but Disconnect returned E_FAIL (0x80004005). Preserving the direct parent during
Dispose alone did not change that result. The close trace shows FormClosing returning while
ProtocolBase's worker is still scheduling the close on the UI thread; native disconnect occurs
inside the later teardown. RDP now requests disconnect synchronously on its UI thread before
that worker starts, with handlers detached to avoid reentrant close and an idempotence guard.
The first connected exit scenarios log a successful early request and pass. The full resource
matrix is still required before accepting this correction.

One separate diagnostic run used dotnet-gcdump to force collection; it is not acceptance
evidence. Its GDI probe ran outside the interactive session and returned zero, so that reading
was discarded. The acceptance battery measures inside its GUI session, rejects zero GDI values,
and never forces collection. Raw dump artifacts remain private and outside the public repository.

The complete unit runner passed 7,381 executions before the early-disconnect addition (groups
overlap, so this is not a unique-test count). One existing window-diagnostic test depended on
pumping unrelated thread messages; its setup now explicitly creates the parent/child handles
and asserts the exact missing-child precondition. No assertions were relaxed or tests skipped.
The latest focused lifecycle/ownership run passed 18 tests; full verification is in progress.

### Further native diagnostics and requested independent review

The complete unit runner also passed 7,381 executions with early disconnect. However, seven
real-session closes still increased GDI objects from 192 to 324. Successful Disconnect alone
therefore does not resolve the remaining retention; no complete-fix claim is justified.
A temporary, balanced IUnknown probe measured 18 native references before teardown and 15
after host disposal for a connected session, versus 12 and zero for an initialized but never
connected control. These counts neither identify the owners nor authorize extra Release calls.

At the maintainer's renewed request, one independent counteropinion was obtained from Mistral
(`mistral-medium-latest`, high). It endorsed comparing immediate disposal with waiting for
OnDisconnected in an isolated STA form without UI Automation. Its confidence in teardown timing
exceeds the evidence: the cause is still unproven, and its suggestion to test IOleObject.Close
is a diagnostic hypothesis, not an approved product fix. Microsoft documents an event wait for
[RequestClose](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpclient-requestclose),
while [Disconnect](https://learn.microsoft.com/en-us/windows/win32/termserv/imstscax-disconnect)
also documents disconnection through closing the control window. Neither proves this leak's cause.
The comparison is now running after correcting the diagnostic delegate binding; the initial
two harness failures happened before connection and provide no teardown evidence.
