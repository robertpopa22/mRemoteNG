# #198: new mixed-DPI evidence

[Reporter reply, September 30](https://github.com/robertpopa22/mRemoteNG/issues/198#issuecomment-5906730267)
read in full after the maintainer pointed it out. This is separate from #182.

The report is from a remote Windows session with 96/192 DPI monitor transitions. At startup the
main menu is already 4.5 pt and the dock font 4.13 pt. At 192 DPI the dock font becomes 8.25 pt;
on returning to 96 DPI it becomes 4.13 pt again. The task dialog's 11.75 pt instruction font is
reduced to 5.88 pt, and its 8.25 pt checkbox font to 4.13 pt. These are observed values, not
proof that the displayed text is half its intended size: WinForms itself scales font point
sizes during per-monitor transitions. The initial interpretation of these values as necessarily
incorrect was withdrawn after checking the [.NET 10 Control source](https://github.com/dotnet/winforms/blob/release/10.0/src/System.Windows.Forms/System/Windows/Forms/Control.cs)
(`GetScaledFont`, `GetCurrentFontAndDpi`, `WmDpiChangedBeforeParent`).

One shown dialog reports DeviceDpi 96 while its checkbox still reports 192, with a 28-pixel
client size. Later dialogs report coherent 96 DPI but the fonts are already halved. Layout
restores the design width from 217 to 424 pixels. The mismatched checkbox DPI persists through
the first `shown (after layout)` entry, so it cannot be dismissed as only a transient entry in
the middle of parent/child scaling. The earlier layout check at 96 DPI did not cover this state.

Investigation: trace font assignment and WinForms per-monitor scaling across creation, first
show and 192-to-96 transitions; reproduce the actual rendering mismatch before another edit. Keep
the menu/dock fonts and the emulated task dialog as separate symptoms. The current lab has
only a 96-DPI console; that cannot certify the reporter's mixed-monitor remote session.
No additional reporter data is needed before examining these paths. No new fix or release
has been claimed, and the issue remains open.
